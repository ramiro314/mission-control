Slow upstart-web-frontend Warm

Question: "The warmup is taking very long for upstart-web-frontend. Can you look into it?" Investigated 2026-11-11 against Warm 63c465ad-79fc-462d-9f6c-646a0e62174e.

Almost all of the time is the copy-on-write seed, not the install. Each slot spends about 30 minutes in the seed step and about 20 seconds in yarn workspaces focus.

The seed clones each seed path with /bin/cp -c -R, which clones one file at a time. A source slot holds about 509k entries, and on this machine the clone ran at about 165 entries per second. On the same tree, one clonefile(2) call on the directory took 0.41 s against 77 s and produced an identical tree.

At that rate the 7-slot Warm runs for about 3.5 hours. No code or config was changed: you chose a report only, with the live Warm and the pool config left alone.

Where the time goes

The code path:

  • src/server/worktrees/manager.ts:2626, in seedTree, logs "Seeding copy-on-write…" once the source is held, then calls stageSeed and placeSeed.
  • src/server/worktrees/seed.ts:497: stageSeed clones each matched seed path one after another.
  • src/server/worktrees/seed.ts:310: on darwin the clone argv is cp -c -R <src> <dst>, spawned by copyOnWriteClone (line 320).
  • src/server/worktrees/seed.ts:382: then removeExclusions walks the whole staged clone in JS to remove **/node_modules/.cache. This step was not timed.

This pool's claim, read-only from app_config.worktrees, seeds node_modules, apps/{personal-loans,my-account,top-of-the-funnel}/node_modules, packages/*/node_modules and .yarn/install-state.gz, with a 60-minute timeoutMinutes. That timeout leaves room for the seed to finish, which is why the Warm is slow rather than failing.

Why per-file cloning is this slow here

cp used under 10% CPU, so it was waiting rather than computing. CrowdStrike Falcon (com.crowdstrike.falcon.Agent) and endpointsecurityd are running. A per-file clone generates one file-creation event per entry, and a directory clonefile avoids those per-entry events. That fits the 190× gap, but it is an inference: see Limits.

A secondary finding: cp -c can byte-copy

The comment at src/server/worktrees/seed.ts:307 says the argv "clones and only clones", and the seed's design rule (line 17) is "copy-on-write or nothing". The macOS cp(1) man page on this machine contradicts that:

-c    copy files using clonefile(2).  Note that if the source and target
      are on different filesystems, or the target filesystem does not
      support cloning, cp will fallback to using copyfile(2) instead to
      ensure the copy still succeeds.

Staging lives in the pool's directory, so source and target normally share a volume, and this is not today's cause. It does mean that a pool on a filesystem that cannot clone would get a silent byte copy instead of the refusal the code promises. This was not reproduced.

Fix options (not implemented)

  1. Clone each seed path with one directory clonefile(2). Node exposes no directory clone, and macOS ships no CLI that makes one (ditto --clone clones "regular files", one at a time). This needs a small Node-API addon beside native/keep-awake and native/state-lock, built by scripts/build-native.mjs and published through publishNativeAddon. The call must run off the event loop (async work or a child process), because a single syscall over 180k entries cannot be interrupted and would otherwise block the daemon. If the addon cannot load, the clone falls back to today's cp -c -R. This option also removes the byte-copy fallback above, because clonefile fails instead of copying.
  2. Operator workaround: drop seed from this pool's claim (PUT /api/worktrees/config, or Settings). Slots then run yarn in place, which took 4 to 60 s in October with yarn's cache warm. A truly empty slot would then pay a full install, which was not measured.
  3. Cancel Warm 63c465ad if the remaining slots are not needed soon. Slots it already warmed stay warmed. You chose to leave it running.

Limits

  • That Falcon causes the slowness is inferred, not proven. Proving it would take a run with a Falcon exclusion for the pool directory, which was not possible here.
  • Only the clone was timed. The JS exclusion walk (removeExclusions), placeSeed's renames, the staging cleanup and slot 11's pre-seed wipe were not timed separately. The 30-minute figure is the whole span from the "Seeding" line to yarn starting.
  • clonefile was benchmarked only on the 13k-entry tree, not on the 149k to 181k-entry trees. How long one call blocks on those, and whether it scales linearly, was not measured.
  • The benchmark of the root node_modules overlapped the daemon's slot-12 clone for about 10 minutes, which probably slowed that slot slightly.
  • Slots 12 to 17 had not finished when this was written, so the 3.5-hour total is an extrapolation from slot 11.
