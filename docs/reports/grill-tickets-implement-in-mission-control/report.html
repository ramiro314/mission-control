Deep dive + proposal · 2026-09-25

/grill-me, /to-tickets and /implement, compared with Mission Control

Question as asked: take the three mattpocock-skills I use most, compare each in depth with what Mission Control offers, and propose how to use them inside Mission Control.

Short answer. Each skill lines up with one stage of Mission Control's own plan-to-ship pipeline, and at each stage the two sides are strong in different places:

  • /grill-me ↔ plan-task decisions. Pocock's interview technique is much better than anything Mission Control has. But it asks its questions in prose, and inside Mission Control a turn that ends in prose is the least visible and least safe place for a question. Mission Control's request_plan_decisions is the ideal way to deliver each round.
  • /to-tickets ↔ phased-plan. These overlap directly and slice work in opposite directions: many thin end-to-end tickets versus the fewest merge-safe phases. to-tickets asks you to approve the breakdown; phased-plan doesn't. phased-plan creates tasks that are actually gated and launched; to-tickets only files tickets. The obvious bridge (GitHub issues → task source) drops the blocking links.
  • /implement ↔ ship task + After-work workflow. /implement is five lines. Four of them fit a ship task. The last one, "commit your work", directly conflicts with the ship contract. And its /tdd step expects a human to confirm the test seams, which nobody may be watching for in an autopilot session.

Proposal: keep Pocock's techniques and Mission Control's plumbing. Concretely: (1) a Mission Control grilling variant that sends each round through request_plan_decisions; (2) teach phased-plan Pocock's slicing rules and add an "approve the breakdown" step; (3) have the GitHub task source import blocking links; (4) a short note on running /implement inside a ship task. Items 1, 2 and 4 are only skill-text changes. Item 3 is a code change. Details in §5.

1. The two pipelines side by side

The stages line up one for one, which is why the skills can be adopted into Mission Control rather than run beside it. Each dashed line is the friction point covered in the sections below.

2. /grill-me in depth

Source: skills/productivity/grill-me/SKILL.md is a one-liner ("Run a /grilling session") with disable-model-invocation: true; the method lives in skills/productivity/grilling/SKILL.md, which the model can invoke itself.

What it actually does

  • Maps the decision as a design tree. Each round asks the whole frontier, meaning every question whose prerequisites are already settled, numbered, each with a recommended answer (❓ Q1 … ➡️ recommendation).
  • Facts are the agent's job, decisions are yours. It sends subagents to look things up instead of asking you, and it doesn't hold back the questions that don't depend on those lookups.
  • It ends only when the frontier is empty, and it doesn't act until you confirm you understand each other.

Against Mission Control

When the questions comeBefore anything is writtenAfter the draft plan exists (request_plan_decisions sends the plan together with its decisions)
How you answerProse in the chat; the turn ends and waitsStructured: radio buttons and checkboxes, "Other" free text, Submit or Dismiss, in the dashboard, with a notification. The call blocks until you answer

A turn that ends on prose questions in a ship task looks like an idle session to Foreman, and its "keep pre-PR ship tasks moving" nudge (20-min quiet window) can push the work on without your answersA plan-decisions review can't be approved by Foreman: classifyPending gives any non-input review canSend: false and says "You cannot auto-approve" (src/server/foreman/pending.ts:143). Verdict: Pocock's method is better and Mission Control's channel is better. The grilling round format maps almost field for field onto request_plan_decisions decisions: question → question, choices → options, ➡️ → recommended: true, open answer → allowOther.

Source: skills/engineering/to-tickets/SKILL.md (user-invoked only). Compared with skills/phased-plan/SKILL.md in this repo.

The bridge that looks like it works, but doesn't

to-tickets → GitHub issues labelled ready-for-agent → a Mission Control GitHub task source filtering on that label → backlog. This files the tickets, but the blocking links are lost: the source asks gh for number,title,body,url,labels,assignees,updatedAt only (src/server/task-sources/github-issues.ts:40), so every ticket arrives with no dependencies. With autopilot allowed on that source, blocked tickets could be dispatched in parallel. With autopilot off (the default), you have to re-enter the links by hand (Edit N tasks → dependencies). Linear isn't a task source at all (only GitHub and Jira), and .scratch tickets aren't read.

Verdict: for work Mission Control will run, phased-plan is the better destination because its tasks are gated and launched automatically. to-tickets is better at deciding the slices and at getting your approval of them. The two gaps worth closing are both in Mission Control.

5. Proposal

Pocock's techniques go into the stages Mission Control already owns. Nothing new runs beside the pipeline, and none of Mission Control's gates are bypassed.

P0 · Use them today, no changes (recipe)

  • Grill: do it in a chat dispatch (ends only when you end it, no ship contract) or at the start of a plan task ("grill me before writing the plan"). Don't grill inside a ship task.
  • Tickets: for work Mission Control will run, keep using the plan → phased-plan path. Use /to-tickets when the tickets are meant for people or other tools on GitHub or Linear. If you do sweep them in, keep autopilot off on that source and re-add the dependencies.
  • Implement: write the ship intent as "…use tdd at the seams and run a code-review before finishing; do not commit, Mission Control handles delivery". That keeps the useful parts and drops the conflict.

P1 · A grilling mode delivered through the dashboard (skill text only)

Add a grill section to skills/html-plans/SKILL.md, or a small new skills/grill/SKILL.md, that keeps Pocock's method and changes the channel: each frontier round is one request_plan_decisions call. The draft plan so far goes in as plan; each question becomes a decision with the recommended option first, recommended: true, and allowOther: true. Subagents still look up the facts. Stop when the frontier is empty, then write plan.md and run the normal review, which already ends with the phased-plan follow-up.

Why this channel: Foreman can't approve a plan-decisions review (verified in pending.ts); you get a notification; answers are recorded as a form; and a dismissal clearly means "stop". Credit Pocock's grilling (MIT) in the skill.

P2 · Tracer bullets and breakdown approval in phased-plan (skill text only)

  • Take over to-tickets' vertical-slice rules, "refactor first", and the expand–contract recipe for wide refactors. That recipe is the one clear gap in phased-plan's sizing rules.
  • Before create_task, show the phase graph (title, blocked-by, what it delivers) through request_plan_decisions with the to-tickets questions: is the granularity right, are the blocking links right, should anything merge or split. Schedule only on Submit. This closes the approval gap in §3.
  • Keep the ≤200-line single-phase rule. It pulls against "many thin tickets", but the rule exists because each Mission Control phase costs a full workflow and PR cycle, which a Pocock ticket doesn't.

P3 · The GitHub task source imports blocking links (code change: src/server/task-sources/)

When a swept issue lists blocking issues, map them onto dependsOnTaskIds between the tasks that source filed, so the /to-tickets → GitHub → autopilot path keeps its order. Optionally add a "local tickets" source kind that reads .scratch/<slug>/issues/*.md.

Open questions before planning this: how GitHub exposes issue blocking links through gh (not checked); what happens when a blocker is closed upstream but has no Mission Control task; and whether cross-source links should be allowed. Worth taking to a plan task, not straight to implementation.

Not recommended

  • Importing these skills as Personas. Persona calls have no tools, and all three skills need tools and a conversation.
  • A new task kind for "grill". Chat and plan already cover it; a new kind means a new contract, dispatch rules and tests for no new capability.
  • Letting /implement commit by loosening the ship contract. That contract is what lets Foreman and the workflow own delivery.

Suggested order: P0 now, then P1 and P2 together (one small PR changing only skill text), then P3 as its own plan task.

That last one follows from the documented gates, which require a settled-idle cycle and exclude "a human ask", but prose isn't a structured ask. I didn't reproduce it.
  • No runs were done. The proposals are untested designs, and none of them has been implemented.
