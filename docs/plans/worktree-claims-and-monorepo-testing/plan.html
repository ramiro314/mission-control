Worktree claims, Warm, and monorepo testing settings

  • Status: approved 2026-10-13, repair rounds 1 and 2 applied, nothing implemented; tickets follow after merge
  • Date: 2026-10-13
  • Source of truth: docs/plans/worktree-claims-and-monorepo-testing/plan.md; this page is its rendering

A pool slot should arrive with the dependencies its commit needs, and a monorepo that will not commit .mission/testing.json should still get an affected-tests gate. This plan adds a per-pool claim that runs on every lease, a Warm action that prepares idle slots ahead of time by cloning dependencies from a sibling, stored testing settings per repository and subdirectory, per-app affected-test selection, and bulk documents for configuring Commands and testing settings in one step.

The prompt was upstart-web-frontend (uwf), a Yarn 4 and Turbo monorepo with 25 apps and 2 packages. It runs Mission Control Commands per app through repository and subdirectory overrides in Library › Commands, with nothing committed to uwf. Its checks fail on missing or stale node_modules (seen: capital-markets failing on @octokit/auth-app). The setup command cannot install a monorepo, and the affected-tests gate needs a committed file that uwf will not accept.

Settled through a three-round grilling session (46 decisions, listed at the end). Where the answer differs from the recommendation offered, the decision table says so. The human approved the plan as written on 2026-10-13 and chose to create tickets after it merges (see "Plan review"). A workflow repair round then added the handoff between slice 3 and slice 4, and crash recovery, from three further human decisions (see "Repair round 1"). A second added how each caller of acquire waits on a long claim, from two more (see "Repair round 2").

Goals

  • A leased slot has dependencies installed for its commit, whoever leased it: a task, a check, or a manual session.
  • A slot whose dependencies already match pays nothing. A cold slot is seeded copy-on-write from an idle sibling instead of paying a full monorepo install.
  • The registry credential an install needs reaches the install, and nothing else does. In particular it does not reach the third-party build scripts the install runs.
  • A failed install never removes a slot from the pool, and a check can tell "this branch broke its lockfile" from "the registry or the token failed".
  • A repository can have an affected-tests gate configured entirely in Mission Control, per app.
  • A monorepo change runs each touched app's tests in that app, with that app's import aliases.
  • A dozen override rows can be configured from one document, written by the operator or proposed by an agent and approved by the operator.

Non-goals

  • Secret storage. Mission Control stores variable names, never values. Values come from the daemon's environment or the login shell, as decided in round 3.
  • Hardening tokenless loopback writes to /api/*. This plan corrects the docs that overstate the boundary and records the hardening as a follow-up (round 1, loopback-writes).
  • Jest moduleNameMapper resolution. Selection resolves aliases through tsconfig/jsconfig paths and workspace package names, and nothing else.
  • Storing the flakes block. Only the CI flake-report action reads it, and CI cannot read Mission Control's database.
  • Committing uwf's configuration anywhere. uwf is the motivating case. Proof is fixtures and e2e (round 3, uwf-acceptance).
  • Changing when the setup command runs, or its limits. Setup still runs once, on slot creation. Only its environment changes (round 2, setup-env).

Background: how things work today

Pools and leases

  • WorktreeManager.acquire (src/server/worktrees/manager.ts:503-776) screens candidates, reserves a slot under the pool lock, then works under the slot lock:

    1. it resets a reused slot (checkout --force --detach, reset --hard, clean -fd) or adds a new one;
    2. it runs setupArgv only for a new slot (:708-722);
    3. it proves path, common dir, exact HEAD, clean and detached (:724-743);
    4. it grants the lease with store.finalizeLease.

  • The setup runner (manager.ts:145-159) has a 120 s timeout and a 64 KiB maxBuffer. An overflow counts as a failure, and a failure quarantines the new slot. Its output is discarded apart from stderr in last_error.

  • Setup runs with the full daemon environment. runSetup passes no env, so every *_TOKEN variable reaches it. Checks get scrubCheckEnv (src/server/workflows/check-env.ts:116-148) followed by agentSubprocessEnv. There is no allowlist.

  • Occupancy. Any process whose cwd is inside an available slot makes the next acquire quarantine that slot (manager.ts:599-601). Setup argv is explicitly not an "own" process (own-processes.ts:11-14). Background work in a slot must therefore hold the slot under a lease.

  • Quarantine has no "unquarantine" action. A slot leaves quarantine only by an owner Return or by Destroy.

  • acquire has three callers:

    • task dispatch (dispatcher.ts:2437), which every task kind, ensemble and Foreman dispatch reaches;
    • check attempts (workflows/check-lease.ts:553);
    • manual leases (POST /api/worktrees/manual/acquire, used by make session).

    A check the pool refuses falls back to a cold git worktree add --detach with no setup (check-lease.ts:434-482). Pipelines do not use the pool.

  • Pool policy {enabled, maxSlots, setupArgv} is WorktreesConfigSchema (src/shared/protocol.ts:2834-2937). It lives in the worktrees app-config entry, keyed by Git common dir, and settings backups already capture it. Lowering maxSlots never prunes.

  • The UI is src/web/components/WorktreeSettingsPanel.tsx. Slot actions are Copy path, Open terminal, Return and Destroy. The action vocabulary is closed (return | prune | reconcile | destroy | legacyReturn). Mutations go preview, then execute, through WorktreeOperationsService (operations.ts:970-1051), whose operation views have queued, running and failed states and Dismiss, but no output and no cancel. The only event is the content-free worktrees_changed, and inventory stays out of MissionState.

  • Nothing records a slot's dependency state. scripts/worktree-setup.mjs checks only whether node_modules exists.

uwf's installed tree

These facts are from reading the main checkout and pool slots read-only on 2026-10-13.

  • Root node_modules is 3.1 GB, with nodeLinker: node-modules, nmMode: classic and enableGlobalCache: true.
  • Every symlink is relative, including .bin entries and workspace links such as node_modules/uwf-my-account -> ../apps/my-account. So is every location in node_modules/.yarn-state.yml and .yarn/install-state.gz. A full search found zero absolute symlinks. A clone of the dependency trees therefore works in place in a sibling slot.
  • Absolute paths appear only in disposable caches: .next, and node_modules/.cache/storybook (135-359 MB per app). Node-gyp .pyc files also carry them, which is harmless.
  • APFS, so cp -c (clonefile) works. The pools live on the same volume as ~/code.
  • There are no workspace lifecycle scripts. Third-party ones exist: esbuild, sharp, dd-trace, @datadog/*, protobufjs, @bugsnag/cli, msw, core-js and others. An allowlisted token is visible to every one of them if the install that runs them has it.
  • .yarnrc.yml references its two environment variables with ${VAR:-} fallbacks, so a Yarn step run without the token still parses its configuration.
  • There is no root tsconfig.json. Each app's tsconfig is standalone, with no extends, and has its own paths (@components/*, @hooks/*, and others).
  • The daemon started from a shell has ARTIFACTORY_AUTH_TOKEN (checked for presence only). The executable locator's login-shell snapshot reads only PATH today (src/server/executables/locator.ts:130).

Checks and affected tests

  • Command resolution. resolveWorkflowCommand (src/shared/workflow.ts:3545-3566) picks the longest applicable override. Overrides are keyed by absolute canonical path, either the main checkout's realpath or a subdirectory below it. The command runs in that subdirectory of the leased tree.
  • Run budget. maxRuns counts executions (workflow.ts:3100-3114). An infrastructure retry is the same execution asked again, capped at MAX_INFRA_ATTEMPTS = 3 (engine.ts:87, 1713), after which the run blocks with infrastructure_error.
  • Testing config. readTestingConfig (src/server/testing-config.ts:37) reads the committed .mission/testing.json from the check tree and .mission/testing.local.json from the main checkout. A missing committed file skips the gate. mergeTestingConfig (src/shared/testing-config.ts:124-146) replaces key by key, list for list. The schema is strict, its keys are tests.{patterns, includeImporters, smokeSet} and flakes.*, and the header calls it a cross-phase contract.
  • Selection. Selection is one per repository, at the tree root (workflows/affected-tests.ts:76, 88). Files reach {files} relative to the override's subdirectory, so a file outside it arrives as ../… (:163). Aliases resolve only through <treeRoot>/tsconfig.json, with no extends, no nested tsconfigs and no workspace packages (src/server/test-selection.ts:122-147).
  • Agent writes. set_affected_tests_command is the only Command write exposed over MCP. It is restricted to testing-setup tasks and writes only the repository-root override. The HTTP routes behind it accept any loopback caller without a token (routes.ts:1598-1603), and docs/security.md:3-6 describes the loopback Host check.
  • Commands catalog. It is DB-only: workflow_commands and workflow_command_overrides, edited in src/web/workflows/CommandLibrary.tsx, with whole-slot compare-and-swap. There is no import or export.
  • Backups. src/server/settings-backups/catalogs.ts captures the Commands catalog. A new relational catalog needs a backup domain and a missing-domain migration so older snapshots still restore (precedent: withSlotsAddedSinceSnapshot, restore.ts:106-133).

Decisions this plan supersedes

  • docs/plans/flake-aware-testing/plan.md:95-96 says "Selection settings are knowledge about the project, so they are committed to the repository and reviewed like code." For the tests.* keys, stored settings now overlay the committed file key by key (round 2, testing-precedence). The committed file is still read, and is still the only source of flakes.
  • docs/worktrees-and-checks.md:413-417 says a check is "a build rather than an install". That is true only after something has installed, and the claim is that something.
  • The "one Command write an agent may make" wording (src/shared/protocol.ts:6456, src/server/testing-setup.ts:1, routes.ts:5037) holds for the MCP tool surface only.

Design

1. The claim: dependency steps on every lease

Settings. The claim is per pool, with no global default (round 3, claim-defaults). It is stored beside setupArgv under worktrees.repositories[<commonDir>], so backups capture it with no new domain:

"claim": {
  "steps": [
    { "argv": ["yarn", "install", "--immutable", "--mode=skip-build"], "env": ["ARTIFACTORY_AUTH_TOKEN"] },
    { "argv": ["yarn", "rebuild"], "env": [] }
  ],
  "timeoutMinutes": 10,
  "fingerprintPaths": ["yarn.lock", ".yarnrc.yml", "package.json", "apps/*/package.json",
                       "packages/*/package.json", ".yarn/releases/**", ".yarn/patches/**"],
  "seed": {
    "paths": ["node_modules", "apps/*/node_modules", "packages/*/node_modules", ".yarn/install-state.gz"],
    "exclude": ["**/node_modules/.cache"]
  }
}

That is the uwf configuration this plan has in mind. It is illustrative and was not run against uwf. yarn rebuild running every skipped build from the cache without the token is the expectation to confirm when someone configures uwf.

  • steps is an ordered list of argvs, never a shell (round 3, claim-steps). Each step names the variables it may receive, and any failing step fails the claim.
  • timeoutMinutes covers the whole claim. It defaults to 10, and the schema caps it at 240 (round 2, claim-limits, Other answer).
  • fingerprintPaths and seed are explained below. An empty fingerprintPaths means the claim always runs.
  • The schema stays .strict() and bounded like setupArgv (32 arguments of up to 4096 bytes each), with caps on steps, variable names and globs that the slice sets.

Where it runs. Inside acquire, under the slot lock, after reset or add and after setup on a new slot, and before the final proof. Every lease kind runs it (round 2, claim-lease-kinds):

  • task dispatch;
  • check attempts;
  • manual leases;
  • the cold check fallback in check-lease.ts, which runs the same claim against its disposable worktree.

There is no extra concurrency limit, so parallel checks claim in parallel and the slot count bounds them (round 2, claim-concurrency).

Environment. Each step runs with scrubCheckEnv then agentSubprocessEnv, the same base as a check (round 1, deps-env). On top of that base it gets only the variables its own env list names (round 3, claim-steps):

  • A value comes from the daemon's environment, else from the login-shell snapshot. The locator's shell read is extended to capture the named variables alongside PATH (round 3, allowlist-source).
  • The pool settings show each name as present or missing, never its value.
  • The setup command moves onto the same base, with setup's allowlist being the union of names the pool lists (round 2, setup-env). This is a behavior change for a setup command that relied on an unlisted credential, and the release notes say so.

Stdin is closed, as it is for checks.

Fingerprint. A slot's fingerprint is a hash over three inputs (round 2, fingerprint):

  • the git blob ids of every path matching fingerprintPaths at the leased commit, read with git ls-tree from objects, not the checkout;
  • every step's argv;
  • every step's variable names.

The claim records it on the slot row only after every step succeeds. A claim whose fingerprint equals the slot's recorded one skips the steps entirely.

Dependency state, written ahead. The slot row gains these nullable columns, added in migrate() next to their upgrade path:

  • deps_state, one of never, current, claiming, seeding, failed or interrupted;
  • the fingerprint, and the commit it was taken at;
  • the last claim's outcome and tail;
  • deps_log_path, the last Warm's log.

Before any claim step or seed touches the tree, one durable write sets deps_state to claiming or seeding and clears the fingerprint (repair round 1). Success writes the new fingerprint with current, and failure writes failed. A crash at any point therefore leaves no fingerprint for a later lease to trust. Recovery is in section 2, "Crash and restart recovery".

Interrupted dependencies (repair round 1, interrupted-deps). A claim that finds deps_state = interrupted first removes the pool's seed.paths, then proceeds as cold: it seeds if a sibling qualifies, else it runs every step.

  • git check-ignore verifies every matched path is ignored before it is removed.
  • A matched path that is tracked, or not ignored, is never removed. The claim fails with a warning instead, under the ordinary failure rules.
  • A pool with no seed.paths has nothing to remove, and the claim runs every step.

A Stop, timeout or Cancel decides deps_state by when it lands:

  • during a seed, it sets interrupted, because the renames may be half done;
  • during a step, it sets failed, like any failed claim, and the next claim reruns the steps in place.

Output and limits. Each step's output streams into a 4,000-byte tail, the same bound and TailRing as checks (check-spawn.ts:254). Output size never fails a claim. A timeout kills the process group and counts as a failed claim.

Failure. A failure is a non-zero exit, a timeout, or a Stop. The slot is handed over with a warning and is never quarantined for the exit code (round 2, claim-failure):

  • The slot's fingerprint is cleared, so the next claim runs the steps again.
  • A task lease is granted. The task card shows the warning and tail, and the agent's launch prompt gets a short note naming the failing step with its output tail (round 3, agent-warning).
  • A manual lease is granted, and the warning is returned to the caller.
  • A check lease does not run the check's Command. The attempt records a dependency failure with the tail, and the verdict rule below decides what it means.
  • A claim that leaves a tracked file modified, or a branch attached, still fails the final proof and quarantines the slot as today. Claim steps must not rewrite tracked files, and --immutable is how uwf's first step honors that.

Check verdict on a failed claim (round 2, claim-check-verdict):

  • If any fingerprintPaths blob differs between the check's head and its merge base with the base branch, the change owns the failure. The check fails, with the tail as its output.
  • If none differs, it is infrastructure. The engine's existing infrastructure path retries it, up to MAX_INFRA_ATTEMPTS, and the run budget is handed back, as for a selection that ran nothing.
  • A pool with no fingerprintPaths treats every failed claim in a check as infrastructure (round 3, no-fingerprint-verdict).

Stop. A running claim has a Stop control on its slot card and on the task card of the dispatch waiting on it (round 3, claim-stop). Stop kills the process group and hands the slot over as a failed claim, so the dispatch continues with the warning.

What the operator sees (round 2, claim-progress-ui):

  • Slot card. The slot view gains a dependency state: current, stale versus origin's default branch, never installed, installing (with the running step and elapsed time), failed (with the tail), or interrupted (a restart, or a Stop or Cancel during a seed; the next claim starts cold). Stale is computed against the last fetched origin/<default> ref, so building the inventory never fetches. Changes reach the dashboard through the existing worktrees_changed revision bump.
  • Task card. The task view carries a provisioning phase while its dispatch waits on a claim: "Installing dependencies", with the step and elapsed time. It arrives through the existing task_upsert event. After the lease, a failed claim leaves a warning on the task.

Who waits on a claim, and for how long

A claim can run for up to 240 minutes inside WorktreeManager.acquire, and acquire takes no AbortSignal (manager.ts:503-509). Each of its three callers was checked for whether it tolerates that (repair round 2):

Caller What waits today What changes
Task dispatch. dispatcher.ts:2437, reached by every task kind Nothing outside the dispatcher. TaskManager.dispatch starts it with void this.dispatcher.dispatch(id, options) and returns (tasks.ts:3423). create, ensembles and pipeline starts do the same. The task sits in dispatching, with no runtime timeout. Startup reconcile already covers a dispatching task (tasks.ts:581-583). The dispatcher's 30 s ready wait starts only after provisioning (dispatcher.ts:875) Tolerated as is. Cancelling a dispatching task stops its running claim, like Stop. Today a cancel is noticed only after provisioning (dispatcher.ts:574), so it would otherwise wait out the claim. A dispatching task still counts toward Foreman's session limit while it claims (foreman/backlog-machine.ts:152-158)
Check attempt. check-lease.ts:553, including the cold fallback The attempt's runAttempt, inside the daemon-wide check limiter (checkLimit, engine.ts:1098-1107), which allows 2 at once (DEFAULT_CHECK_CONCURRENCY, checks.ts:172). The command's timeout starts at spawn, after the lease (check-runtime.ts:326). So claim time never counts against it, and a slow install ends as a dependency failure under the claim's own timeout, never as a timed-out check While the claim runs, the attempt gives up its check slot, and it takes one again before the command spawns (repair round 2, check-claim-limiter). The ladder order, the budget reservation and the test lease are unchanged. Cancelling the run stops the running claims of its attempts. Today cancelRun only updates the database

The script's fetch has no timeout (new-session.mjs:70-77), and Node's built-in fetch gives up after 300 s without response headers. The script then prints "Mission Control is not running". The route never reads the request's abort signal, so the lease is still granted, to an owner nobody holds. Manual owners survive restarts until an explicit return (owners.ts:53-63), so the slot leaks The route accepts, then the client polls (repair round 2, manual-acquire-shape), described below

The manual route, when the pool has a claim. This is the shape the existing worktree operations already use: 202, then the client polls.

  • POST /api/worktrees/manual/acquire pins HEAD as today. It then returns 202 with a requestId, and runs the acquire in the background under the same manual:<key> owner.
  • GET /api/worktrees/manual/requests/:requestId returns one of three states:
    • claiming, with the running step and elapsed time;
    • granted, with the lease and any claim warning;
    • failed, with the reason.
  • new-session.mjs polls every 2 s and prints the step and elapsed time. It treats a 404 after a 202 as "the daemon restarted while claiming". The slot is then recovered by crash table row 1.
  • A request granted but not polled within 10 minutes is returned by the daemon. It uses the ordinary owner-authorized return with requireClean and an occupancy check, so a lease nobody received cannot leak. An occupied slot stays leased.
  • Pending requests live in daemon memory. After a restart, a granted lease that was never picked up is an ordinary manual lease, which Settings › Worktrees shows and can Return.
  • Compatibility. A pool with no claim configured still answers 201 with the lease, synchronously, as today. A new-session.mjs from an older checkout therefore keeps working against a newer daemon for every pool that has not opted in. The script accepts both 201 and 202.

When the daemon, not the caller, stops waiting. A running claim holds its slot's lock, so three more rules follow.

  • Claim registry. The manager keeps an in-memory registry of running claims, keyed by slot, with each claim's owner and process group. Stop, task cancel, run cancel and shutdown all find claims through it.
  • Maintenance. Periodic maintenance takes every slot lock in turn (manager.ts:1048) before it reclaims leaked leases, and it reschedules only after finishing (manager.ts:1505-1513). It skips a slot whose claim holds the lock, instead of waiting on it, records the slot as skipped in the reconciliation record, and retries it next pass.
  • Shutdown. engine.stop() and worktrees.stop() have no deadline today (engine.ts:635, manager.ts:1540-1544). Shutdown kills every running claim's process group first and grants no lease while stopping.
    • The slot stays provisioning, with deps_state = claiming or seeding. The next startup applies crash table row 1 or 2: quarantine, and interrupted.
    • This is the same cost a restart during setup has today.

2. Seeding and Warm

Why a maintenance lease. Because of the occupancy rule, nothing may run inside an available slot. Warm and seed sources therefore hold their slots under a new lease owner kind, warm, alongside task, check and manual. A warm lease is granted and released through the same finalizeLease and release paths, and it is never visible as a task.

When to seed (round 3, warm-seed-when). A Warm or a claim seeds from a sibling when either of these holds:

  • the target has no recorded fingerprint, because it is new, was never warmed, or its last claim failed;
  • the target's fingerprint is stale and an idle sibling's fingerprint matches the target commit's exactly.

Otherwise the claim runs in place, so a small lockfile change stays an incremental install. Claims seed under the same rule as Warm (round 2, seed-on-cold-claim), including the cold check fallback.

Choosing the source (round 2, warm-source):

  • The first choice is an idle sibling whose fingerprint matches the target commit's. The next is the idle sibling most recently claimed successfully.
  • The source is held under a warm lease for the length of the copy. It returns to the pool through the ordinary release path afterwards.
  • The main checkout is never a source.
  • If no sibling is idle, or no idle sibling has a fingerprint, there is no seed. The claim steps run alone.

Copying (round 2, seed-copy):

  • The copy is copy-on-write only: cp -c -R on macOS and cp -R --reflink=always on Linux. Where the filesystem cannot clone, the seed is skipped, never replaced by a byte copy.
  • The copy covers only the operator's seed.paths globs, matched in the source, and seed.exclude removes paths from the clone before it is placed.
  • Each matched path is cloned into a staging directory in the pool's directory, on the same volume and outside the checkout. The existing target path is then removed and the staged copy renamed into place. The checkout never holds a half-copied tree.
  • After a seed the target inherits the source's fingerprint, and the claim's ordinary skip rule decides whether the steps run.
  • A failed clone is not a failed claim. The seed is abandoned and its staging removed, and the steps run.

Warm (round 2, warm-scope, warm-output; round 3, warm-target):

  • Warm has two triggers:
    • Warm on an available slot's card;
    • Warm idle slots on a pool row, which warms every available slot of the pool.
  • Both go through preview and execute in WorktreeOperationsService, so the action vocabulary gains warm.
  • A Warm takes a warm lease on the target, fetches, resets the slot to origin's current default branch, seeds or claims under the rules above, then releases.
  • The operation view gains a live output tail and a Cancel control:
    • The tail is updated with a worktrees_changed bump at most once per second while a Warm runs.
    • Cancel kills the process group and returns the slot to the pool as available. The fingerprint was already cleared by the write-ahead, and deps_state follows the Stop rule in section 1.
  • The full log is written under the state directory, at logs/worktree-warm/<operationId>.log.
    • The operation view links it.
    • The target slot's deps_log_path keeps the most recent log reachable from the slot card, including after a restart.
    • A log no live operation and no slot row references is removed.
  • Warm never touches a leased or quarantined slot. A slot leased while a "Warm idle slots" operation is queued is skipped and listed as skipped.

Crash and restart recovery (claims, seeds and Warm)

The native-worktree contract applies unchanged: persist intent before mutation, reconcile every transitional state at startup, quarantine ambiguity (docs/plans/native-worktree-management/plan.md:190-193, 444). This plan adds two intents:

  • deps_state (section 1);
  • the warm lease, owned by warm:<operationId>.

Whether a warm owner exists. Warm operations live only in daemon memory (WorktreeOperationsService keeps them in a Map), so no Warm operation survives a restart.

  • At runtime, nativeWorktreeOwnerReferenced reports a warm owner as referenced exactly while its operation is queued or running.
  • At startup reconcile, which runs before the operations service accepts work, it reports a definite "not referenced". It never reports "unknown".

Crash points. Startup reconcile handles each one deterministically:

Crash during Durable state startup finds Startup does Afterwards
Claim steps inside a task, check or manual lease slot provisioning, deps_state = claiming, no fingerprint Quarantines "interrupted provisioning intent", as today; sets deps_state = interrupted If the slot later returns to the pool, its next claim wipes the seed paths and starts cold
A seed inside a lease, including between renames slot provisioning, deps_state = seeding, no fingerprint Same as above Same as above
A Warm on its target slot leased by warm:<op>, deps_state = claiming or seeding Owner provably absent, so the ordinary return path runs: occupancy check, reset to origin's default, clean and detached verification. The slot becomes available with deps_state = interrupted (repair round 1, warm-restart) Its next claim wipes the seed paths and starts cold
A seed, on its source slot leased by warm:<op>, deps_state unchanged The same return path. A source is only read, so its fingerprint stays valid The ordinary skip rule
Any of the above, with doubt unknown occupancy, a claim or seed process still running in the slot, a dirty tree, or a failed verification Quarantine, as today Return or Destroy, as today
A claim in the cold check fallback check-lease attempt row check-lease's existing recovery removes the disposable worktree, and the attempt is infrastructure Nothing to carry over: the fallback has no slot row
Seed staging directories under <pool dir>/.seed-staging/ Removed n/a
Warm log files under logs/worktree-warm/ Kept while a slot row's deps_log_path names it, otherwise removed n/a

Two further rules.

  • Orphaned processes. A claim step's process group can outlive a crashed daemon. Its cwd is inside the slot, so the occupancy check sees it and the slot is quarantined. It is never handed out.
  • Task card. The task card's "Installing dependencies" phase is not persisted, so a restart drops it. The dispatch's existing recovery reports the outcome.

3. Stored testing settings

Catalog (round 2, testing-storage, testing-flakes):

  • A new table, testing_settings, holds repo_root (primary key), settings_json, revision, created_at and updated_at.
  • It is keyed by the same canonical path as Command overrides, either the main checkout's realpath or a subdirectory below it.
  • settings_json is validated by a new StoredTestingSettingsSchema in src/shared/testing-config.ts. It allows only tests.patterns, tests.includeImporters and tests.smokeSet, all optional, .strict(), and within the existing limits.
  • The committed and local schemas and mergeTestingConfig do not change incompatibly. The CI action keeps bundling them.

Layers.

Scope Lowest Then Highest
Repository root committed .mission/testing.json (check tree) stored settings at the root .mission/testing.local.json (main checkout)
Subdirectory (apps/my-account) the root's merged result stored settings at that subdirectory none
  • Stored settings overlay the committed file key by key (round 2, testing-precedence, against the recommendation). The local file stays the operator's last word at the root (round 3, testing-layer-order).
  • A subdirectory's stored keys apply to files inside that subdirectory (round 3, testing-subdir-semantics):
    • A key it sets replaces the root's value there.
    • Its patterns and smokeSet are relative to the subdirectory.
    • A key it does not set falls through to the root.
  • Nested subdirectory scopes apply nearest first.
  • The local file stays flat and root-only.

Behavior.

  • The gate runs when any layer exists at any scope. With no committed file and no stored settings it is skipped, as today.
  • An invalid stored row cannot be saved: the route validates it on write. The committed file's rules stay as they are: an invalid committed file fails the gate, and an invalid local file makes it unavailable.
  • Run detail labels the source of every effective key: committed, stored (<scope>) or local. This extends today's settings.localKeys.
  • flakes is never stored, and continues to come from the committed file or its defaults.

UI.

  • The settings are edited on the affected-tests page in Library › Commands (CommandLibrary.tsx), as a "Testing settings" section listing the root and every subdirectory that has stored settings or an affected-tests override.
  • Each row edits patterns, includeImporters and smokeSet. A stale save is refused with 409 and the row reloads.

Backups (round 2, backups). A new settings-backup domain, testing-settings, with a missing-domain migration so snapshots taken before it restore with the domain empty.

Scopes and the test universe. This ships with stored settings, in slice 3 (repair round 1, slice3-subdir-handoff).

  • resolveTestingScopes(treeRoot, repoRoot) is the server module that resolves the layers above into TestingScopes. That is a browser-safe type in src/shared/testing-config.ts holding the ordered scopes, each with:
    • its repository-relative path;
    • its effective settings;
    • the source of every key.
  • scopeOf(path) returns a file's nearest scope.
  • The test universe. Per scope, the tests are the tracked files matching that scope's effective patterns, resolved relative to the scope that set them. A file belongs to its nearest scope. includeImporters and smokeSet apply per scope in the same way.

The selector in test-selection.ts takes TestingScopes in place of one flat config.

Until slice 4 lands, the gate behaves like this:

  • Subdirectory settings take full effect on which tests are selected.
  • Selected files still run through today's single invocation. That is the one override the session's cwd resolves, with files relative to its subdirectory (../… outside it), exactly as today.
  • Import scanning still resolves aliases through the root tsconfig.json only. A per-app alias import therefore does not yet select its importer, and run detail says so in the selection diagnostics.

Slice 4 consumes TestingScopes and resolveTestingScopes unchanged. It adds per-app resolution and partitioning on top of them.

4. Per-app affected-test selection

Resolving imports (round 2, alias-resolution).

  • tsconfig and jsconfig. For each scanned file, test-selection.ts finds the nearest tsconfig.json or jsconfig.json at or above the file's directory, stopping at the tree root.
    • It follows relative extends, and package extends it can resolve inside the tree.
    • An unresolvable extends is reported in the selection diagnostics, not fatal.
    • It uses that config's paths and baseUrl. It keeps today's extension and JS-to-TS swaps.
    • It fixes the first-*-only wildcard replacement (:165).
    • It caches parsed configs per gate.
  • Workspace packages. The root package.json workspaces globs (array or {packages} form) map each workspace's name to its directory.
    • A bare specifier name resolves through the workspace's package.json: a string exports for ., else main, else index.
    • A specifier name/sub resolves inside the workspace's directory.
    • Package exports maps beyond a single string are out of scope for this slice and are reported in diagnostics.
  • Resolution still refuses anything outside the tree.

The test universe comes from section 3's resolveTestingScopes, which this slice consumes unchanged. The resolver changes above do not change any scope's universe. They change which of its tests includeImporters selects, because more imports now resolve.

Partitioning (round 2, selection-unit). The gate selects once across the repository, then assigns each selected test to the deepest affected-tests override whose subdirectory contains it:

  • A test outside every subdirectory override goes to the repository-root override, or to the slot's global default, which runs at the root.
  • A test no override or default can run is listed in run detail as selected but unrun. The gate decides on the partitions that ran (round 3, uncovered-tests).
  • Each partition runs its own override's command in that override's subdirectory, with {files} relative to it. {junit} gets a temporary path per partition, and results map back to tree paths.
  • Partitions run sequentially, all of them, inside the one check-test lease (round 3, partition-order). Each partition reruns its failed files once, as today.
  • The gate passes only if every partition passes.
  • The gate attempt spends one run of the budget however many partitions it has (round 3, partition-budget). An attempt that selects nothing hands the run back, as today.
  • Run detail lists each partition: its subdirectory, command, file count, outcome and output tail.

Partitioning does not depend on the session's cwd. The change decides which apps run. The session's cwd still decides which test, lint, typecheck and build override a check uses, as today.

5. Bulk documents for Commands and testing settings

Format (round 3, bulk-format). The format is versioned JSON, with its schema in src/shared beside the other wire contracts:

{
  "version": 1,
  "commands": {
    "lint":           [{ "path": "", "argv": ["yarn", "turbo", "run", "lint", "--filter=...[origin/main...HEAD]"] },
                       { "path": "apps/my-account", "argv": ["yarn", "lint"] }],
    "affected-tests": [{ "path": "apps/my-account", "argv": ["yarn", "test:affected", "--junit-file={junit}", "{files}"] }],
    "test":           [{ "path": "apps/legacy-app", "remove": true }]
  },
  "testing": [
    { "path": "apps/my-account", "settings": { "tests": { "patterns": ["src/**/*.test.{ts,tsx}"] } } },
    { "path": "apps/old-app", "remove": true }
  ]
}
  • path is repository-relative, and "" is the root.
  • The affected-tests argv above is a placeholder. A real one must contain {files} as a whole element and {junit} somewhere (commandTemplateProblem, src/shared/workflow.ts:3205), and how an app's Jest writes JUnit to a given path is for whoever configures it.
  • The target repository is chosen when the operator imports, or is the proposing session's task repository.
  • Each entry is checked against the rules its catalog already enforces: the template rule for affected-tests, duplicate refusal and the override cap.
  • A document sets Command overrides for every slot, plus stored testing settings, for one repository (round 2, bulk-coverage). It never touches global defaults, maxRuns or pool settings.

Applying (round 3, bulk-apply):

  • Rows the document does not mention are untouched. A listed row is added or replaced. Removal happens only through an explicit remove entry.
  • The preview lists every add, change and removal, per slot and for testing settings.
  • Apply writes everything in one transaction, using each slot's compare-and-swap and the testing catalog's revisions. A preview that went stale is refused with 409 and recomputed.

Two producers, one screen (round 2, bulk-mode):

  • Import. The operator pastes or uploads a document in Library › Commands, picks the repository and gets the preview.
  • Export. Library › Commands exports a repository's current overrides and testing settings as a document (round 3, bulk-export). Export then import round-trips.
  • Proposal. A new MCP tool, propose_command_document, takes a document from a session (round 3, bulk-proposal-rules):
    • It accepts only the calling session's own task repositories, using the guard set_affected_tests_command already uses, without the testing-setup label restriction.
    • It never writes a live row. It stores one pending proposal per repository, and a newer one replaces it.
    • The proposal shows as a banner on that repository in Library › Commands and as an attention item. Opening it leads to the same preview, where the operator applies or dismisses it.
  • Pending proposals are machine state and are not in backups.

The approval step is a boundary on the MCP surface only. The apply route is under /api/*, which accepts any loopback caller without a token, and the docs say so plainly (section 7).
