Linux readiness: remove Mission Control's macOS assumptions

Status: approved 2026-10-12 after a three-round interview with the human (decisions D1 to D22 below) and a plan review that approved it as written. Follow-up chosen in the review: Create tickets after the plan merges, so Mission Control slices it into tickets in a linked follow-up task once this plan's pull request merges. Amended the same day in plan-validation repair round 1 (R1 to R5), repair round 2 (R6 to R11) and repair round 3 (R12 to R14), all below, and after GitHub Inspector's review of PR #438 (R15). Not implemented.

Goal

Mission Control was built and run on macOS. Its operator now runs it on Linux. This plan records every place the repository assumes macOS, what each one does on Linux, and how each gets fixed, so that Linux is a first-class platform with no silent breakage (D1): every feature either works on Linux or is hidden or labeled as unavailable there, and nothing appears to work and then fails.

macOS behavior does not change (D3). Linux is added as rows in the existing platform seams, or as explicit platform branches where no seam exists, and every Linux branch has a twin unit test pinning the macOS result (D22).

Where things stand (verified 2026-10-12 on main at b030421d)

The operator's machine. Arch Linux x86_64, KDE Plasma on Wayland, zsh, Node 26 through mise, Claude Code at /opt/claude-code/bin/claude. Installed: Ghostty 1.3.1, tmux, a running Herdr server, xdg-open, systemd-inhibit, notify-send, wl-copy, lsof. Not installed: WezTerm. Mission Control runs as make start (daemon, Vite, Foreman and Electron under electronmon) from ~/Dev/mission-control; the daemon reports v1.26.0 on port 7317.

The platform seams. Fork feature #422 ("Platform seams") put process inspection (src/server/process-inspection/), process lifetime (src/server/platform/process-lifetime.ts), the executable environment (src/server/platform/executable-environment.ts) and native addon sources (scripts/native-addon-sources.mjs) behind one per-platform map each. Every map is empty, so Linux resolves to the POSIX row, which was written on and for macOS. A Linux row plugs in there. #422's contract says "each seam's platform-selection map is empty", so any ticket that adds a Linux row also changes #422 (see Fork tracking).

Already Linux-aware, not to be re-fixed.

  • Process groups and tree kills (process-lifetime.ts); ps flags on procps-ng 4.0.7; TTY matching of pts/N; check identity from /proc (src/server/workflows/check-identity.ts); evidence images verified through /proc/self/fd (src/server/workflows/images.ts).
  • The state-lock addon builds and loads on Linux (flock, renameat2, linkat).
  • tmux and Herdr adapters. Herdr explicitly allows Linux (src/server/terminal/herdr.ts:22-28).
  • Resume guard and leases: LC_ALL=C, uid, mode and symlink checks (src/server/terminal/resume-lease.ts:44-60).
  • The browser open target uses xdg-settings, gtk-launch and xdg-open (src/server/open-targets/browser.ts:116-167).
  • Symlinked temp dirs: every comparison is realpath-based; nothing hardcodes /private.
  • The archive watcher falls back from recursive watch; the conductor tail tolerates a zero birth time.
  • Keep Awake reports "unavailable" with a reason instead of failing, and its native build is skipped on Linux.
  • The interrupt shortcut (⌃C) already yields to a text selection, so Ctrl+C still copies on Linux (src/web/lib/keybindings.ts:352,732).
  • Electron: every menu accelerator is CmdOrCtrl; shell.openExternal, notifications, single-instance reveal and the integrations installer work.
  • Paths: state lives in ~/.mission-control; temp files use os.tmpdir(); nothing writes to ~/Library.
  • CI runs unit, build-smoke and e2e on ubuntu-latest; Electron renderer and geometry tests run there under xvfb-run -a with --no-sandbox.
  • Shipped skills/, hooks/, integrations/, personas/ and actions/ contain no BSD-only shell flags or macOS paths.

Fix groups

Ordered by tier, as D6 asks. Each group is a candidate ticket, or a small set of them; the follow-up task slices them. "Default fix" marks an item D18 confirmed without its own question. Every group that adds a Linux branch also adds a twin test pinning the macOS result (D22), and every UI change carries a Playwright spec, per AGENTS.md.

T1: harm or daily breakage

F1. Headless runs leave the shared temp dir (S1, S2)

  • On Linux, HEADLESS_CWD becomes a private directory under the state dir, <state dir>/headless (mode 0700, created on demand). runClaudeText, the Codex runners and the Pi model catalog use it as their cwd. On macOS it stays tmpdir() (D13: moving it would move macOS transcripts to a new encoded project dir).
  • The pruner derives its directory from HEADLESS_CWD through claudeProjectDir, so on Linux it prunes the new encoded dir and never touches ~/.claude/projects/-tmp/ again. Existing -tmp transcripts are left alone (D21); the docs and the PR say they can be removed by hand.
  • The "Deliberately accepted" comment in goal/prune.ts is rewritten: on Linux the directory is now exclusively Mission Control's.
  • Tests: platform-injected unit tests for the cwd choice and the pruned directory on both platforms; a pruner test proving a -tmp transcript older than 24h survives on Linux.

F2. Inspector deny list and private state dirs (S3, S4)

  • Deny rules.

    • The .ssh, .aws and .claude rules are built from os.homedir() (//${home}/.ssh/**) instead of //Users/*, and **/.credentials.json is added. On macOS these resolve to the same paths, so they apply everywhere (D13).

    • The state-dir rule differs by platform (R11). The Inspector's cwd is the PR's worktree or repo root (liveDir, src/server/inspector/worker.ts:340-344). Dispatched worktrees live inside the state dir: worktree-pools (WORKTREE_POOLS_DIR) and the git-worktree fallback worktrees (WORKTREES_DIR), both in src/server/config.ts:23-26. A blanket //${home}/.mission-control/** rule would therefore deny the Linux Inspector the worktree it is reviewing, which today's inert Linux rules do not.

    • On Linux the state-dir rule must fail closed, not depend on what happens to exist (R15). It is rooted at the resolved state dir (stateDir(), which honors MISSION_HOME) and has two parts:

      1. A named list, always denied whether or not the entry exists. These are the entries the code defines at b030421d:
        • files: harness.db, harness.db-wal, harness.db-shm, token, scout-submission.key, scout-producer.json, install-receipt.json, pi-extension.json, daemon.lock, daemon.log, foreman.log, update.log;
        • directories, each with /**: backups, archives, uploads, workflow-evidence, scouts, scout-submission-credentials, ask-channel, installers, bin, check-worktrees, pi-extension.lock.d.
      2. Every other top-level entry present when the Inspector spawns, apart from the two carve-outs, worktrees and worktree-pools. This catches entries the named list does not know about yet.

      The list is computed at each Inspector spawn, where the grant is built (worker.ts:208), not once at module load as the DENY_PATHS constant is today. An entry created after the daemon starts is therefore covered from the next spawn.

    • On macOS the rule stays //Users/*/.mission-control/** and DENY_PATHS stays a constant, unchanged, because a carve-out would change macOS behavior (D13). That rule also covers macOS's dispatched worktrees today; this is recorded as S13 and left out of scope.

    • F1's headless cwd (<state dir>/headless) is never an Inspector cwd. A grant always carries the worktree or repo root (src/server/llm/claude-sdk.ts:186 falls back to HEADLESS_CWD only without a grant), and headless runs hold no tools. That it sits under the state-dir rule is therefore correct and harmless.

    • llm-runner-contract.test.ts pins the exact rendered string per platform and is updated with it.

  • One resolver for the private roots (R9). The roots are derived in three places today:

    • DISPOSABLE_STATE_ROOT (src/server/agent-subprocess-env.ts:35), used by the daemon only;
    • isolatedScoutSubmissionCredentialPath and sessionScoutCredentialDirectory (src/shared/harness-runtime.mjs:208,232), used by the daemon and by MCP children that resolve their own credential path;
    • scouts/submission-auth.ts:94,124, which writes through the harness-runtime paths.

    They are replaced by one agentRuntimeRoot(name) in src/shared/harness-runtime.mjs, which every process imports. The resolution order is:

    1. MISSION_AGENT_RUNTIME_DIR, which the daemon sets to the root it resolved, both in every launch env and in the env of the MCP config it hands an agent, so a child never re-derives a different root;
    2. on Linux, $XDG_RUNTIME_DIR/mission-control (per-user, 0700, not aged out);
    3. tmpdir(), which is macOS's only source, so macOS is unchanged.

  • Ownership check, everywhere (D13). The resolver lstats the root and refuses it unless uid === getuid(), it is not a symlink, and (mode & 0o077) === 0. That is the rule resume-lease.ts:44-60 already applies. On macOS's private $TMPDIR it is a no-op.

  • Refusal. A refused root fails closed and never falls back to another directory, so an attacker cannot steer the choice:

    • in the daemon, the launch or credential provisioning that needed it fails with "Mission Control refused <path>: owned by uid N with mode M; remove it and retry", surfaced through the existing launch-error path (src/server/terminal/launch-error.ts);
    • in an MCP child, the credential read returns empty, which is today's "no credential provisioned" path, and the daemon's log names the refused root.

  • Upgrade of in-flight sessions.

    • Disposable state homes keep today's lifetime: the old daemon's exit hook removes its live homes (agent-subprocess-env.ts:hookProcessCleanup), as on any restart. On Linux, reconcileDisposableAgentStateHomes sweeps both the new root and the legacy /tmp/mission-control-agent-state.
    • Capability files are the one cross-version reader: an MCP child started before the upgrade keeps resolving the legacy /tmp/mission-control-agent-capabilities path. On Linux, while that legacy root exists and passes the ownership check, the daemon writes each capability file to both roots. The legacy root disappears at reboot on tmpfs /tmp (Arch), or through systemd-tmpfiles ageing elsewhere, and the dual write stops when it is gone.

  • Tests:

    • deny-rule rendering per platform, including that the Linux rules never cover worktrees or worktree-pools;
    • with an empty state dir, every named entry is still denied (R15);
    • an entry created in the state dir after module load is denied at the next Inspector spawn;
    • a source guard test finds every state-dir entry name the code defines (join(STATE_DIR, "...") and join(stateDir(), "...")) and fails unless each one is in the named deny list or is one of the two carve-outs, so a later change that adds a state-dir entry has to classify it;
    • the resolver order (env override, XDG_RUNTIME_DIR, temp dir) on both platforms;
    • an MCP child given MISSION_AGENT_RUNTIME_DIR reads the credential the daemon wrote;
    • the ownership check refuses a foreign-uid, group-writable or symlinked root with the message above;
    • the Linux dual write to an existing, owned legacy root, and no write to a foreign one.

F7. The source checkout as the Linux install (E6, E8, I1 to I4, W7)

  • systemd user unit. install-service on Linux writes ~/.config/systemd/user/mission-control.service, which runs the existing scripts/start-service.mjs (daemon only, as launchd does today) with the resolved Node. It runs systemctl --user daemon-reload and enable --now; --uninstall reverses it. Logs go to journald. macOS keeps launchd. The unit:

    [Service]
ExecStart=<resolved node> <checkout>/scripts/start-service.mjs
WorkingDirectory=<checkout>
Restart=always
RestartSec=2
RestartPreventExitStatus=75
[Install]
WantedBy=default.target

  • Graphical environment under the unit (R6). The unit carries no display variables, and it is wanted by default.target, not graphical-session.target, because a window manager that never reaches graphical-session.target would never start it.

    • Every GUI program the daemon spawns goes through one graphicalSessionEnv() helper. That covers xdg-open and gtk-launch in open-targets/browser.ts, F5's ghostty and xdg-terminal-exec / $TERMINAL adapters, and WezTerm on Linux.

    • Two sources, chosen per spawn (R13). One source is the user manager's current environment, read with systemctl --user show-environment at that spawn. The other is the daemon's own environment. Each spawn takes WAYLAND_DISPLAY, DISPLAY, XAUTHORITY, DBUS_SESSION_BUS_ADDRESS, XDG_CURRENT_DESKTOP and XDG_SESSION_TYPE as one set from a single source, never mixing the two, so a stale XAUTHORITY cannot pair with a live DISPLAY. The order:

      • Under the user manager (the unit; systemd sets INVOCATION_ID), the manager's current environment comes first and the daemon's own is the fallback. A service started or restarted mid-session inherits the manager's values at that moment, and only the manager learns about a later login, so its own copy goes stale.
      • Outside the manager (make start, make up), the daemon's own environment comes first and the manager's is the fallback.

    • A dead display counts as absent. A source is usable only when its display socket exists:

      • WAYLAND_DISPLAY resolves to $XDG_RUNTIME_DIR/<name>, or the absolute path it names;
      • a local DISPLAY :N resolves to /tmp/.X11-unix/XN;
      • a remote host:N display is taken as present.

      A source whose socket is gone is skipped, so after a logout with linger on, neither source is usable and the named error below fires instead of a client connection error.

    • Reading at spawn time covers a unit that started before the desktop imported its environment into the user manager. KDE Plasma and GNOME import it at login; other sessions run dbus-update-activation-environment --systemd, which F13 documents. Because the manager comes first under the unit, it also covers a later login with a new display.

    • When neither source has a usable display, the action fails with "No graphical session is reachable from the Mission Control daemon: neither the daemon nor the systemd user manager has a WAYLAND_DISPLAY or DISPLAY whose socket exists. Log in to a desktop session, or start the daemon from one." This appears where Focus and open-target errors appear today.

    • The helper is Linux-only; macOS spawns are unchanged.

  • Lifetime at logout.

    • Without linger (the default), the user manager stops when the user's last session ends. That stops the unit and every systemd-run --user --scope server with its agents, which matches macOS, where logout ends the LaunchAgent and the session's processes.
    • With linger (loginctl enable-linger), the unit and the scoped servers keep running after logout. The old display sockets disappear with the session, so GUI actions fail with the message above until the next graphical login. After that login, the manager's environment, read first under the unit, holds the new display.
    • F13 documents both.

  • Long-lived children leave the launcher's cgroup (S10, R14). On Linux, when systemd-run resolves, the following run under systemd-run --user --scope in app.slice, each in its own scope:

    • tmux and Herdr servers that Mission Control starts;
    • every GUI program spawned through graphicalSessionEnv(): the ghostty raise (both +new-window -e and the ghostty -e fallback), xdg-terminal-exec, $TERMINAL -e, WezTerm, and xdg-open / gtk-launch, which can start the browser itself when it is not already running.

    Without systemd-run, they start as today. This lands in F7 with the unit, never after it. Otherwise systemctl --user stop, or a Restart=always restart after a crash, would kill every server the daemon started with every agent inside it, and close every terminal window Focus opened and any browser an open target started. The same wrapper also takes them out of a terminal's surface scope when the daemon runs under make start.

  • Desktop entry (D19). A new Make target builds dist/ and installs ~/.local/share/applications/mission-control.desktop, which runs the checkout's Electron against the built bundles with no MISSION_DEV_SERVER_URL. It uses build/icon.png from F4. Updating is git pull && make build.

  • Adopt, wait or supervise (R7). Today the shell probes /api/health once and spawns its own daemon when nothing answers (startDaemon, src/main/daemon.ts). It then starts Foreman in both cases (ownElectronBackgroundStart, src/main/daemon-policy.ts). A unit and an autostarted shell both start at login, so on Linux the shell adds one step:

    • A daemon answers: adopt it, as today. Quitting the shell leaves an adopted daemon running (its stop is a no-op).
    • Nothing answers: run systemctl --user is-active mission-control.service (1 s timeout).
      • On active, activating or reloading, do not spawn. Poll the health probe every 500 ms for up to 30 s and adopt. On timeout the startup page says the service is running but not answering, and names journalctl --user -u mission-control.
      • On anything else (inactive, failed, not installed, or no systemctl), supervise its own daemon and Foreman as today.
    • The unit's main process is the daemon (R12). scripts/start-service.mjs builds the native addons in a child process, then imports src/server/index.ts into its own process (scripts/start-service.mjs:3-5,57-60: "load the daemon into this process so launchd owns and signals its exact PID"). The exit status 75 below is therefore the main process's exit status, which RestartPreventExitStatus acts on, with no wrapper status to propagate. The daemon's process.pid, which /api/health reports, is the unit's MainPID.
    • State-lock contention gets exit status 75 (EX_TEMPFAIL) instead of today's uncaught contentionError from acquireStateOwnership (src/server/index.ts:134). The unit's RestartPreventExitStatus=75 makes a unit daemon that loses the lock stop instead of restart-looping into the failed state. On Linux, the shell's supervisor treats 75 as "another daemon owns this state": it re-probes and adopts instead of restarting. launchd and the macOS shell restart on 75 exactly as they do on today's exit 1, so the macOS effect is identical (D13), and the shell's handling of 75 is a Linux branch.

  • Start at login. On Linux the tray checkbox reads and toggles ~/.config/autostart/mission-control.desktop, a copy of the desktop entry. It is disabled with a hint when the desktop entry is not installed.

  • macOS-only refusals. make install, make app, make install-app, npm run package, scripts/install.sh and recover-database refuse Linux up front with one message: "the packaged app is macOS only; on Linux run from a checkout (see docs/setup.md)". make help marks them "[macOS]". The updater's Linux reason says the same. The bundle-path code in E8 stays darwin-only and is guarded rather than ported.

  • Tests:

    • install-service unit tests for the Linux unit text and the systemctl calls through a fake (twin of the launchd test);
    • desktop-entry and autostart file contents;
    • refusal messages per platform;
    • the adopt / wait / supervise decision with systemctl and the health probe injected, and the supervisor's handling of exit 75, on both platforms;
    • graphicalSessionEnv() on Linux:
      • under INVOCATION_ID the manager's environment wins over a set own environment;
      • outside the manager the own environment wins;
      • a stale own-environment display (socket missing) falls through to the manager's;
      • both sources stale gives the no-display message;
      • the variables come as one set from one source;
    • the scope wrapper's argv for each GUI spawn path and for the tmux and Herdr servers, with and without systemd-run, and macOS unchanged;
    • manual, on the operator's box:
      • the entry launches from the KDE menu and adopts a systemd daemon;
      • with the unit disabled and no daemon running, the entry supervises its own daemon and Foreman, and quitting the shell stops both;
      • with the unit enabled and autostart on, a fresh login yields exactly one daemon: the health pid equals the unit's MainPID from systemctl --user show -p MainPID;
      • after a fresh login, with the daemon running only under the unit, Focus raises Ghostty on a tmux session;
      • systemctl --user restart mission-control leaves running tmux and Herdr sessions, their agents, a terminal window opened by Focus, and a browser started by an open target, all alive and open;
      • with linger off, logging out ends the unit and the scoped servers.
